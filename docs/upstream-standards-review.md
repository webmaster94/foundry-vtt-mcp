# Upstream standards and architecture review

Reviewed upstream `cbca58ce369cd5e6f1a90edb3aacc40f4cdf6d7c` against common base `259d402b30d8eee16453dbb444c97d1b8bf76398`, with local `799a4a8` as the compatibility target. This is a read-only code assessment. No upstream runtime changes were imported and no live Foundry claims were tested.

## Recommendation

Do not merge this upstream range wholesale. The fork has a smaller, generic Game API, transactional desktop configuration, centralized server routing, and a stronger transport implementation. Upstream retains specialized tool families and a different installer. Adapt isolated fixes only after reproducing their failure through our current API.

## Import requirements

Any selected adaptation must retain the routing facade and central `runWithServer` behavior. New writes need the existing permission guard, audit record, and feasible inverse/dry-run support. Tool definitions must remain within the smoke test's 70,000-character catalog limit. New Foundry behavior needs live verification, especially v14 document shape changes; upstream mocked tests alone do not establish compatibility.

The most useful upstream contribution here is a reproducible failure case for chunked responses. The larger transport, installer and CRUD implementations would replace local work with less suitable code. System-specific serialization and actor behavior deserve a separate feature review rather than blanket rejection based on architecture.
